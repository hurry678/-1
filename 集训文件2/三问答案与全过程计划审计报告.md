## 一、审计结论

本次审计只依据题目 PDF、全过程计划、三问详细实施计划以及问题 1—3 目录内的答案、代码、CSV、JSON 和结果工作簿。审计不以报告中的“通过”声明替代底层证据复核。

总体结论为：**全过程计划的约束口径和验收思路基本正确，但三问现有答案不能整体判定为可提交。** 问题 1 的调度结果在已比较方案中有效，问题 2、3 完成了任务并生成了较完整日志，但仍存在足以否决提交的硬问题：

1. 问题 3 出现跨 Link 最小车身净空 **139 mm**，低于题目规定的 300 mm，差额为 **161 mm**。现有审计只检查同一 Link 上车辆间距，因而把该违规漏判为 0。
2. 问题 2、3 的逐步轨迹 `QuestionNo` 全部错误写成 1：问题 2 共 **373,520 行**，问题 3 共 **423,200 行**，相应 CSV 与结果工作簿均受影响。
3. 问题 1、2 的程序和独立验证只在离散步端点检查同 Link 间距，未实现题目要求的步内连续最小间距证明；“零违规”只能解释为“已检查项目未发现违规”，不能解释为任意时刻安全。
4. 问题 2 正式方案平均任务执行时间为 **148.045253 s**，劣于滚动插入的 **145.008411 s**；问题 3 正式方案为 **856.908420 s**，劣于直接复用问题 2 的 **834.963753 s**。两问均未按题面主目标选择已运行方案中的最优可行方案。

## 二、严重度与判定规则

| 严重度 | 定义 | 处置 |
|---|---|---|
| P0 | 违反题目硬约束、提交字段错误或足以使结果无效 | 修复前禁止引用性能结果和提交工作簿 |
| P1 | 未满足主目标、关键证明或独立验收缺失，可能改变方案结论 | P0 清零后修复并全量重跑 |
| P2 | 复现、统计、文档一致性或扩展实验不足，不必然推翻可行性 | 正式定稿前补齐 |

“通过”必须同时满足数据、任务、轨迹、资源、在线性、模板和复现七类验收。任一硬门失败，平均时间、Makespan、距离等性能数值只可作为故障定位数据，不得作为有效方案成绩。

## 三、统一硬约束验收标准

### 3.1 数据与任务

1. 数据规模固定为 131 个 Node、152 条 Link、36 个 Port、20 辆 OHT；问题 1—3 任务数分别为 32、190、600。
2. P17 必须在构图和建缓存前覆盖为 `(Node70, Link507, 303 mm)`；不得残留原始异常值 `(Node69, Link505, 1473 mm)`。
3. 每项任务唯一完成一次；取货后不得换车；同一 Carrier 后继任务只能在前序完成放货后进入可分配集合。
4. 所有位置必须在所在 Link 的合法偏移范围内，正常任务路径不得进入 TERMINAL。

### 3.2 运动学与安全

1. 任意时刻速度满足所在 Link 限速；加速度范围为 `[-3000, 2000] mm/s²`。
2. 车长为 950 mm，车尾到后车车头的净空不得小于 300 mm；等价的同参考点路径距离不得小于 1250 mm。
3. 安全验收必须覆盖同 Link、相邻 Link、跨多个短 Link、汇流前后、CurveGroup 出入口和 Port 队列，不能只按 `CurrentEdgeID` 分组。
4. 对每个 0.2 s 步，按两车相对位置函数求区间内最小值；若加速度在步内分段，则按分段区间逐段求极值。仅检查步首、步末不构成题目第 5.2.9 条要求的证明。
5. 跨 Link 距离按有向路径累计。对于相邻 Link，后车参考点到前车参考点距离至少应为“后车当前 Link 剩余段 + 前车在下游 Link 的偏移”；净空再减去 950 mm。

### 3.3 资源与服务

1. Port、MERGE、CurveGroup 任意时刻容量均不得超过 1。
2. 取货、放货各连续 8 s；服务车辆占据 Port，后车不得穿越。
3. CurveGroup 必须在前车车尾完全离开后释放；MERGE 未获权车辆必须在上游可制动位置停车。
4. 资源验收应由轨迹反推实际占用区间，不以 owner 字段或预约日历自证。

### 3.4 在线性

1. 问题 2、3 在决策时刻只能读取 `InstallTime ≤ DecisionTime` 的任务。
2. 除日志断言外，必须做反事实测试：随机修改所有未来任务的 Source、Destination、Priority、CarrierID 和行序，当前时刻之前的决策摘要哈希应完全不变。
3. 已发生的空驶、等待和重规划必须保留；取货后 VehicleID 不得改变。

### 3.5 输出与复现

1. 任务表问题号分别为 1、2、3；逐步轨迹每一行和指标表对应行也必须使用同一问题号。
2. 每个 StepNo 恰有 20 辆车；时间步连续；CSV 与 Excel 行数、值和时间格式一致。
3. 指标必须从底层事件重新聚合，并与任务结果表双向核对。
4. 固定代码版本、依赖版本、配置、随机种子、输入哈希和运行命令；干净目录全量重跑后输出哈希一致，或仅允许已声明的运行时间差异。

问题 1—3 均实现 Port、MERGE、CurveGroup 的 owner 或预约控制。问题 2 记录 4679 条资源预约事件，等待图最大 10 条边；问题 3 记录 5245 条底层预约事件、4580 个计划时隙、4444 个实际使用时隙、226 次时隙平移，日志中实际时隙重叠错误为 0。

### 5.6 在线性

缺失项：步内连续安全证明、未来任务反事实、候选方案完整轨迹和同等级独立审计。

结论：**当前正式输出不可提交。修复模板和安全证明后，应按主目标改选滚动插入，或进一步优化完整主模型直至不劣于它。**
